小林 @ 机器人问周末爱好，几秒后又补一句：「我是说很久以前提到的那个。」模型还没回第一条。谁决定第二条要不要立刻开一场新对话？等轮到第二条时，又是谁决定是否查记忆？这两个问题分别落在程序调度和模型决策两层。

| 术语                      | 在本项目中怎么理解                                                                                                                    |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent（智能体）**       | 对话回合可以由模型根据当前输入选择下一步，例如调用搜索、读取记忆、发言、沉默。                                                        |
| **Workflow（工作流）**    | 程序预先编排步骤；步骤中也能使用模型。日记从读取素材、生成到分目的地发布，是一个例子。                                                |
| **Harness（运行支撑层）** | 本课程用它指包围模型的应用代码：事件入口、上下文组装、工具权限、调度、终止和投递。这是一个架构视角，仓库中没有专门叫 `Harness` 的类。 |

## 先区分三种职责

先想一个简单的程序：收到 `/roll` 就在允许的范围内掷骰子，再把数值发出去。每次结果可能不同，路径却是程序提前写定的，随机性没有让它变成 Agent。工作流也可以在固定路径中加入 AI，例如「取当天素材 → 调用模型写日记 → 保存 → 发布」。生成的句子会变，但模型不负责决定去哪个地方发布。

再看群聊回合。除了直接写回复，模型可能先发出查资料的请求，读过结果再决定怎么回答。我们用 **Agent（智能体）** 指这类由模型根据当前信息选择下一步的行为。选择空间可大可小；小林直接问自己的过去时，程序会先指定查询动作，留给模型的是怎样描述查询和如何据结果回答。

**Harness** 是从模型外面看这套应用代码：怎样收到输入、给哪些工具、允许执行多久、出了问题怎么收尾。一个系统可以同时有工作流、Agent 和 Harness，不用强行选一个词给整个仓库贴标签。

## 推演一次调度

假设第一轮已经在跑，后续触发都符合入队条件。程序不让它们绕过第一轮并发抢话：

```ts title="src/libs/group-runtime.ts"
schedulePassiveTurn(turn: ScheduledTurn): void {
  if (this.shutdown.signal.aborted) return;
  this.pendingTurn = turn;
  if (this.state.running) {
    this.state.dirty = true;
    return;
  }
  this.scheduleDebounce();
}
```

`pendingTurn` 保留最新待处理回合。若已有回合在跑，`dirty` 标记之后还得处理新输入；若空闲，`scheduleDebounce()` 先等一小段安静时间，并保留最大等待约束。这些操作在模型收到请求之前完成。[源码：被动调度](https://github.com/yinyanfr/nyarbot/blob/2433deab6c72ea1ccc44b39c22887badfd638fa1/src/libs/group-runtime.ts#L501-L510)

| 时刻                 | 调度器状态                                 | 模型在做什么                               |
| -------------------- | ------------------------------------------ | ------------------------------------------ |
| 小林的第一个回合启动 | `running` 为真。                           | 处理第一轮。                               |
| 第二个合格触发到达   | 更新 `pendingTurn`，标记 `dirty`，先返回。 | 仍在处理第一轮；没有为第二条另开并发调用。 |
| 第一轮释放运行状态   | 如还有待处理任务，重新等待防抖计时。       | 下一轮还没有开始。                         |
| 防抖结束且允许继续   | 调度器启动待处理回合。                     | 模型才开始处理新一轮。                     |

**防抖（debounce）**就是短时间内先等一等、合并密集的触发。`pendingTurn` 保存的是最新待处理的执行任务，并不意味着应用把每条早一点到达的聊天记录都删除。消息是否登记与任务是否合并是两个问题。

主动回合也先经过 `canRunProactive()`，再占用同一个 `running` 状态，最后在 `finally` 中释放。[源码：主动调度](https://github.com/yinyanfr/nyarbot/blob/2433deab6c72ea1ccc44b39c22887badfd638fa1/src/libs/group-runtime.ts#L580-L599) 这个边界决定两个回合会不会抢着向同一个群发言。

## 模型做的决定也有边界

进入 `generateAiTurn()` 以后，模型可在给定工具里选择行为；调用预算、可见用户范围、是否接受工具请求都还由宿主，也就是承载模型的应用程序控制。模型可以提出查询某个编号，但程序必须自己验证这个编号在本轮是否允许访问。把「请不要越界」写进提示只是引导，把限制写到工具执行路径才实际控制了数据访问。

## 动手看

阅读 [`group-runtime.test.ts` 的 `marks dirty` 测试](https://github.com/yinyanfr/nyarbot/blob/2433deab6c72ea1ccc44b39c22887badfd638fa1/src/libs/group-runtime.test.ts#L462-L509)，画出「第一次开始 → 第二条触发到达 → 第一次结束 → 第二次开始」四个节点。第二条到达时，系统应等待模型给一个「排队」的决定吗？如果再来一条合格触发，`pendingTurn` 能同时保存两件待执行任务吗？

<details>
<summary>参考答案</summary>

排队发生在调度代码中，与模型判断无关。`running` 使第二条先等待；第一轮结束后重新防抖，再启动新回合。`pendingTurn` 只有一个槽位，再有合格触发会覆盖该槽内的执行任务。不要把它画成每次点名都必定执行一次的任务队列。

</details>
